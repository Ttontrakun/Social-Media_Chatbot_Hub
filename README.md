# socialmedia_chatbot_hub

ระบบรวมแชทจาก LINE, Facebook, Instagram และ X ไว้ในหน้าเดียว พร้อมบอทที่ตอบจากเอกสารที่คุณอัปโหลด (RAG)

- **Frontend** หน้าเว็บเดียว ไม่ใช้เฟรมเวิร์ก เสิร์ฟด้วย nginx
- **Backend** Node 22 + TypeScript + Express
- **ฐานข้อมูล** PostgreSQL 16 ผ่าน Prisma 7 (driver adapter — ไม่ต้องใช้ engine binary)
- **เวกเตอร์** Qdrant
- **LLM / Embedding** ชี้ไปที่เซิร์ฟเวอร์ของคุณเอง ผ่าน endpoint ที่เข้ากันได้กับ OpenAI

## เริ่มใช้งาน

```bash
cp .env.example .env
# สร้างค่าสุ่มแล้วใส่ใน .env เฉพาะเครื่องนี้
openssl rand -hex 32   # JWT_SECRET
openssl rand -hex 32   # ENCRYPTION_KEY
openssl rand -hex 16   # POSTGRES_PASSWORD และ QDRANT_API_KEY ถ้าต้องการ

docker compose up -d --build
```

เปิด http://localhost:8080 แล้วสมัครบัญชีแรก บัญชีนี้จะเป็นเจ้าของ workspace

หยุดระบบ: `docker compose down` (ข้อมูลยังอยู่) · ลบข้อมูลทั้งหมด: `docker compose down -v`

`.env.example` มีแต่ชื่อตัวแปรและค่าว่างสำหรับความลับ ค่าจริง (รหัสผ่าน, JWT, คีย์เข้ารหัส, API key, token ของ Meta) อยู่ใน `.env` ซึ่งถูกกันไว้ใน `.gitignore` ห้าม commit ไฟล์นั้น

### ต่อกับโมเดลของคุณ

ถ้าไม่ตั้ง `EMBEDDING_BASE_URL` ระบบจะใช้ **โหมดทดลอง** ที่คำนวณเวกเตอร์ง่าย ๆ ในเครื่อง พอให้เห็นภาพรวมทั้งระบบ แต่คุณภาพการค้นหาต่ำมาก ใช้งานจริงไม่ได้ ให้ตั้งค่าใน `.env`

```
EMBEDDING_BASE_URL=https://your-embedding-host/v1
EMBEDDING_API_KEY=
EMBEDDING_MODEL=bge-m3
EMBEDDING_DIM=1024
LLM_BASE_URL=https://your-llm-host/v1
LLM_API_KEY=
LLM_MODEL=your-model
```

`EMBEDDING_DIM` ต้องตรงกับขนาดเวกเตอร์ของโมเดล ถ้าเปลี่ยนทีหลังต้องตั้ง `QDRANT_COLLECTION` เป็นชื่อใหม่ด้วย ไม่งั้นระบบจะเตือนและไม่ยอมเริ่ม

ถ้าไม่ตั้ง `LLM_BASE_URL` บอทจะส่งข้อความดิบจากเอกสารที่ใกล้เคียงที่สุดแทนการเรียบเรียงใหม่

## ระบบอ่านเอกสาร (พอร์ตมาจาก Bingsu_core)

ส่วนอ่านและค้นเอกสารนำมาจากระบบ Bingsu ที่ใช้งานอยู่แล้ว ไม่ได้เขียนใหม่

| ความสามารถ | ทำอะไร |
|---|---|
| ตัด chunk แบบรู้โครงสร้าง | ไม่ตัดกลางตาราง Markdown ถ้าตารางยาวจะหั่นตามแถวและ**ใส่หัวตารางซ้ำทุกส่วน** หัวข้อถูกเก็บไว้กับเนื้อหาของมัน สำคัญกับตารางอัตราค่าบริการที่ถ้าตัดกลางแล้วตอบผิดคอลัมน์ |
| OCR ภาษาไทย | PDF ที่ดึงข้อความได้น้อยกว่า `OCR_MIN_TEXT_CHARS` จะถูกส่งไปบริการ OCR อัตโนมัติ ไฟล์รูปภาพก็ส่ง OCR เช่นกัน ตั้ง `OCR_API_URL` ชี้ไปที่ `Bingsu_core/Backend/Service/Ocr` (PaddleOCR) ได้เลย |
| ขยายคำค้น | คำถามหนึ่งถูกแตกเป็นหลายคำค้นตามคำพ้องความหมาย เช่นถาม "ค่าบริการเท่าไหร่" จะค้นคำว่า "ราคา" ให้ด้วย เพิ่มคำได้ที่ `RAG_QUERY_SYNONYMS` |
| รวมกลับเป็นบล็อกเดิม | เอกสารที่ถูกหั่นหลายช่วง เมื่อค้นเจอช่วงหนึ่งระบบจะรวมช่วงพี่น้องกลับมาด้วย กันกรณีเงื่อนไขหรือข้อยกเว้นอยู่คนละช่วงกับใจความหลัก |
| reranker | ถ้าตั้ง `RERANK_URL` จะเรียงผลค้นหาใหม่ตามความเกี่ยวข้องกับคำถาม แทนที่จะใช้คะแนน vector ล้วน ถ้าเรียกไม่สำเร็จจะกลับไปใช้ลำดับเดิมเอง |
| Excel เป็นตาราง Markdown | ชีตถูกแปลงเป็นตาราง Markdown เพื่อให้ตัวตัด chunk รักษาหัวตารางไว้ได้ |
| embed แบบ batch ขนาน | ส่ง embedding ทีละชุดและยิงหลายชุดพร้อมกัน อัปโหลดเอกสารใหญ่เร็วขึ้น |

หน้า **ความรู้ > ลองถามบอท** แสดงคำค้นที่ระบบขยายให้ คะแนนของแต่ละช่วง และบอกว่าช่วงไหนถูกรวมกลับเป็นบล็อกเดิม ใช้ตรวจก่อนเปิดให้ตอบลูกค้าจริง

ส่วนที่ยังไม่ได้พอร์ตจาก Bingsu: multi-hop decomposition (แตกคำถามซับซ้อนเป็นคำถามย่อย), RAG cache และตารางคำพ้องในฐานข้อมูล เพราะผูกกับโครงสร้างข้อมูลของ Bingsu โดยตรง

## เชื่อมช่องทาง

webhook ต้องเข้าถึงได้จากอินเทอร์เน็ตด้วย https ตั้ง `PUBLIC_URL` เป็นโดเมนจริงก่อน แล้ววาง URL ที่ระบบแสดงให้ลงในแต่ละแพลตฟอร์ม

| ช่องทาง | สิ่งที่ต้องกรอก | Webhook URL |
|---|---|---|
| LINE | Channel ID, Channel secret, Channel access token จาก LINE Developers Console | `PUBLIC_URL/webhooks/line` |
| Facebook | Page ID, Page access token, App secret ของ Meta App | `PUBLIC_URL/webhooks/facebook` |
| Instagram | Instagram account ID (Business/Creator), Page access token, App secret | `PUBLIC_URL/webhooks/instagram` |
| X | User ID, access token, consumer secret | `PUBLIC_URL/webhooks/x` |

Meta จะยิง GET มาตรวจก่อน ต้องตั้ง `META_VERIFY_TOKEN` ใน `.env` ให้ตรงกับที่กรอกในหน้าตั้ง webhook ของ Meta

ถ้าตั้ง `META_APP_ID` และ `META_APP_SECRET` ด้วย จะมีปุ่มเชื่อมผ่าน OAuth ให้เลือกเพจแทนการกรอก token เอง (ต้องผ่าน App Review ก่อนจึงใช้กับเพจของคนอื่นได้)

**ข้อจำกัดของ X:** การรับ DM แบบ realtime ต้องใช้ Account Activity API ซึ่งเปิดให้เฉพาะแพ็กเกจราคาสูง ถ้าแพ็กเกจที่ใช้ไม่มี webhook ต้องเปลี่ยนไปใช้วิธี polling ซึ่งยังไม่ได้ทำในเวอร์ชันนี้

## วิธีที่บอททำงาน

```
ลูกค้าทัก → webhook (ตรวจลายเซ็น) → แปลงเป็นข้อความรูปแบบกลาง → บันทึกลง Postgres
   → ถ้าหัวข้อตรงรายการ "ส่งต่อพนักงานเสมอ" → ส่งต่อคน
   → ถ้าโหมด DRAFT → ร่างคำตอบรอให้แอดมินกดส่ง
   → ถ้าโหมด AUTO → ค้น Qdrant → คะแนนถึงเกณฑ์ไหม
        ถึง    → ส่งเข้า LLM พร้อมเอกสาร → ตอบลูกค้า พร้อมอ้างอิงชื่อไฟล์
        ไม่ถึง → ส่งข้อความสำรอง แล้วส่งต่อพนักงาน
```

บอทจะไม่เดาคำตอบ ถ้าค้นไม่เจอหรือ LLM ตอบ `NO_ANSWER` ระบบจะส่งต่อให้คนเสมอ ปรับความเข้มงวดได้ที่หน้า **ตั้งค่าบอท** (คะแนนขั้นต่ำ)

เมื่อพนักงานพิมพ์ตอบ บทสนทนานั้นจะสลับเป็นโหมดพนักงานอัตโนมัติ บอทจะไม่แทรกอีกจนกว่าจะกดสลับกลับ

## ตัวเลขแจ้งเตือนในรายการแชท

- **สีแดง** ลูกค้ากำลังรอพนักงาน (ขอคุยกับคน, ถูกส่งต่อ, บอทตอบไม่ได้ หรือช่องทางหลุดการเชื่อมต่อ) เคสเหล่านี้ถูกเรียงไว้บนสุด และมีตัวเลขรวมที่เมนู "แชท" กับชื่อแท็บเบราว์เซอร์
- **สีดำ** มีข้อความใหม่แต่บอทดูแลอยู่ ไม่ต้องรีบเข้าไปตอบ

## หน้าต่าง ๆ

| หน้า | ทำอะไรได้ |
|---|---|
| แชท | กรองตามช่องทาง, ค้นหา, สลับโหมด Bot/พนักงาน, ขอให้ AI ร่างคำตอบ, ปิดเคส, แท็กลูกค้า, รับเคส, จำลองข้อความลูกค้าเพื่อทดสอบ |
| ความรู้ | อัปโหลด PDF / Word / Excel / CSV / ข้อความ ดูสถานะการประมวลผล และลองถามบอทพร้อมดูช่วงข้อความที่ถูกอ้างอิงกับคะแนน |
| ช่องทาง | เชื่อม/ตัดการเชื่อมต่อแต่ละบัญชี เปิด-ปิดบอทแยกช่องทาง ดูสถานะ token หมดอายุ |
| ตั้งค่า | บทบาทและน้ำเสียงของบอท, โหมดตอบอัตโนมัติ/ร่างคำตอบ, หัวข้อที่ส่งต่อคนเสมอ, ข้อความสำรอง, ความเข้มงวดของการค้นหา |
| API | สร้าง API key และตั้ง webhook ขาออก (ยิง event เมื่อระบบส่งข้อความหาลูกค้า พร้อมลายเซ็น HMAC) ดูบันทึกเหตุการณ์ |
| สรุป | กราฟจากข้อมูลจริง: ข้อความต่อวันแยกช่องทาง, บอทกับพนักงาน, ช่องทางยอดนิยม, ช่วงเวลาที่ลูกค้าทัก เลือก 7/30 วัน สลับเป็นตารางได้ |

## ความปลอดภัย

- ไฟล์ `.env` ไม่ได้อยู่ใน git มีเฉพาะ `.env.example` ที่ไม่มีรหัสผ่านหรือ API key
- รหัสผ่านเก็บเป็น bcrypt hash
- access token และ channel secret ของทุกช่องทางเข้ารหัสด้วย AES-256-GCM ก่อนลงฐานข้อมูล (คีย์มาจาก `ENCRYPTION_KEY`)
- เซสชันเป็น JWT ใน cookie แบบ httpOnly — ตั้ง `COOKIE_SECURE=1` เมื่อขึ้น https
- API key เก็บเฉพาะ hash ตัว key เต็มแสดงครั้งเดียวตอนสร้าง
- webhook ทุกช่องทางตรวจลายเซ็นก่อนรับข้อความ ลายเซ็นผิดจะถูกทิ้งและบันทึกไว้
- บัญชีของแต่ละแพลตฟอร์มผูกได้กับ workspace เดียว และข้อมูลลูกค้าแยกตาม workspace เสมอ

## เมื่อแก้โครงสร้างฐานข้อมูล

`backend/prisma/schema.prisma` เป็นต้นฉบับ ส่วน `backend/prisma/init.sql` คือ DDL ที่ backend รันตอนบูตเพื่อให้ตารางพร้อมโดยไม่ต้องรัน migration **ถ้าแก้ schema ต้องแก้ init.sql ให้ตรงกันด้วย** หรือจะใช้ migration ของ Prisma แทนก็ได้ โดยตั้ง `SKIP_DB_INIT=1` แล้วรัน `npx prisma migrate deploy` เอง

หมายเหตุ: `prisma generate` ตอน build จะดาวน์โหลด schema engine จาก binaries.prisma.sh ถ้าเครือข่ายปิดทางนั้น ให้ตั้ง `PRISMA_SCHEMA_ENGINE_BINARY` ชี้ไปที่ไฟล์ใดก็ได้ที่มีอยู่จริงเพื่อข้ามขั้นตอนดาวน์โหลด (Prisma 7 ไม่ได้ใช้ engine นี้ตอนรันจริง)

## สิ่งที่ยังไม่มี

- แนบรูปหรือไฟล์ในแชท และข้อความประเภทอื่น (สติกเกอร์, story reply, reaction)
- จัดการทีมหลายคนและสิทธิ์ (โครงสร้างในฐานข้อมูลรองรับแล้ว แต่ยังไม่มีหน้าเชิญสมาชิก)
- สลับหลาย workspace ในบัญชีเดียว
- Graph RAG (ตอนนี้เป็น vector search อย่างเดียว)
- X แบบ polling สำหรับแพ็กเกจที่ไม่มี webhook
